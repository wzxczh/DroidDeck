# Thor 上的 Steam SD 卡预分配

记录于 2026-10-04 的调查。下文的设备测量数据与 PR 状态是当天工作的快照。
所有事件时间均为 EDT（UTC−04:00）。

在 Thor 的 SD 卡上完成了一次全新的 1000xRESIST 安装，使用了原生路径与预分配
回退补丁：2,216 个文件预分配耗时 **6m44s**，随后下载并提交成功，
**总计 16m36s**。观测到的预分配包装函数报告零失败，累计执行时间约 7.1 秒。
该包装函数测量**并未**覆盖整个预分配阶段。

在一次小规模受控探测中，原生目录访问比 Android 的 FUSE 视图快得多。对剩余
延迟期间的内核采样显示了 exFAT 的文件创建与大小更新等待。这支持进一步调查
SD 卡元数据写入。但它并不能证明 PRoot 没有开销、不能证明延迟单独由 `dirsync`
造成，也不能证明 SD 卡现在的安装速度已与内置存储持平。

选定的源日志片段保存在[证据文件](evidence/thor-sd-storage-2026-10-04.txt)中。
原始完整日志包含无关的会话，解读这些片段并不需要它们。

## 最初的报告与预分配失败

[关联的 Discord 报告](https://discord.com/channels/1552707793247539220/1555632840388116491/1556271955076710560)
附带了一个较新的诊断 ZIP，其中包含 `storage.log`。与此前缺少预分配插桩的
抓取不同，这次抓取确认了：

- 所选的次级库是可移动的，其暴露的文件系统是 FUSE。
- Steam 调用了模式为 0 的 `fallocate`，收到 `EOPNOTSUPP`（errno 95）。
- 观测到的该失败在 212 微秒内返回，其本身并不是一次数分钟的阻塞调用。

一次 Thor 基线抓取同样显示 `fallocate` 以 errno 95 失败，耗时 310 微秒。
这些结果确认了在所测路径上预分配 API 不受支持。它们并不能把后续 Steam 的
延迟归因于任何特定的回退方式。

关于 glibc 的 `posix_fallocate` 模拟造成了整个挂起的说法，并未被这些日志
证实。所测的 Steam 调用包括 `fallocate`；目录操作和其他调用发生在该包装
函数之外。

### 原生内容路径与大小写处理：#221

对于配置为 `/storage/...` 的库，启动器会检查对应的 `/mnt/media_rw/...`
候选路径。它要求可用的目录权限，并通过两个视图执行写入/读取/删除的身份探测。
失败时保留原配置路径。

只有共享的 SD 卡内容绑定会发生变化。对于私有前缀、迁移和其他私有存储，
配置路径仍是该库的身份。这样在选择更快的视图时不会移动已有的存档或运行时
状态。可移动卷的检测同样使用原配置路径，因为 Android 的卷 API 未必识别
原生别名。

C 语言快路径仅在不跟随符号链接检查目录组件之后，才允许在已知的
FUSE/FAT/exFAT 文件系统上出现仅大小写不同的规范父目录差异。它同样处理受支持的
`F_OK` 加 `AT_SYMLINK_NOFOLLOW` 情形。仍有歧义的路径会回退到 PRoot。

最终的 #221 diff 涉及四个文件，98 行插入、20 行删除，其中含 28 行新增测试。
实验性的目录缓存已从该 diff 中移除。

### 预分配回退：#229

启动器先在所选内容路径上创建一个临时的 1 MiB 文件，将其扩展，并检查
`st_blocks` 是否报告至少 2,048 个 512 字节块。该文件还必须能被成功清理。
只有通过这一预留探测的可移动库才启用该回退。

对于指向所选库设备的文件描述符，包装函数会先尝试真正的预分配 API。
当模式为 0 的 `fallocate` 返回 `EOPNOTSUPP` 时，它改用 `ftruncate` 扩展文件。
它会校验范围、检测溢出，并避免缩小已存在的文件。其他模式和其他错误保持
原有行为。POSIX 包装函数优先尝试内核预分配以避免不必要的 libc 模拟，并保留
POSIX 的错误返回与 `errno` 语义。

这是一个经能力测试的回退，而不是无条件的预分配成功上报。扩展失败仍会
返回错误。该优化独立于可选的诊断开关运行。

一次预留探测和一次成功的完整安装，并不能取代未来针对 ENOSPC、安装中断
或其他设备/文件系统的单独测试。

### 完整的绑定表：#233

真实的 Steam 会话有 **96 条绑定**。原先 C 实现 64 条的上限会静默丢弃靠后的
映射。其中若干条是共享 SD 卡根目录内的私有覆盖项，因此截断可能把操作发到
错误位置或返回 `ENOENT`。

#233 将容量提升到 256，并使启动器与 C 实现在无法表示完整表时都禁用快路径。
超长路径同样会触发回退而不是部分映射。这既是一个正确性修复，也是信任该存储
快路径的前提。

标记文件只存在于私有目录中。普通应用进程通过以下客体路径读取到它们：

| 库下的客体路径 | #233 之前 | #233 之后 |
|---|---|---|
| `SteamLinuxRuntime_4-arm64` | 正确的私有标记 | 正确的私有标记 |
| `steamlinuxruntime_4-arm64` | 正确的私有标记 | 正确的私有标记 |
| `proton experimental (arm64)` | `ENOENT` | 正确的私有标记 |
| 旧版 `steamapps/shadercache` | `ENOENT` | 正确的私有标记 |

每次成功读取都返回 17 字节的 `private-override\n` 标记。临时标记和辅助
可执行文件事后均已删除。

## 元数据测量说明了什么

元数据是文件系统的记账：名称、目录项、大小和空间分配。Steam 的
`Preallocating` 阶段包含观测到的预分配包装函数之外的工作，包括创建和定位文件。

### 通过原生与 FUSE 路径读取目录

一个辅助程序运行在普通应用进程中，通过宿主的两条路径列出了保存的暂存树中
同一个稳定的资源目录。它利用既有的快路径系统调用跳板绕过 PRoot 的路径转换，
同时保留应用的 Android 权限。读缓冲为 128 KiB。

| 视图 | 耗时 | 成功的 `getdents64` 调用 | 目录字节数 |
|---|---|---|---|
| 原生 exFAT | 约 2.3 ms | 2 | 154,920 |
| Android FUSE | 约 501 ms | 112 | 154,872 |

两个视图返回的字节数略有差异。这是一次以原生优先的单趟测试，并非缓存状态
完全受控的重复基准。它展示的是该次目录读取的巨大成本差异，而不是完整 Steam
安装的相应倍数。

更早的一次 root 列目录发生在并发文件创建期间，测得经 FUSE 约 5.56 秒、原生
9.25 毫秒。其目录当时正在变化，因此证据强度较弱，不作为受控对照使用。

### 文件创建与大小更新

在全新的原生路径 Steam 运行期间，采样到的内核调用栈包括：

```text
__sync_dirty_buffer -> exfat_update_bh -> exfat_init_ext_entry
    -> exfat_add_entry -> exfat_create -> path_openat

__wait_on_buffer -> exfat_update_bhs -> exfat_free_dentry_set
    -> __exfat_write_inode -> exfat_truncate -> do_sys_ftruncate
```

这些是实时采样，不是连续的归因剖析。它们显示了延迟期间在原生文件系统的
创建/更新路径上等待的时间。

一个仅 root 的辅助程序创建了临时目录，随后用
`open(O_CREAT|O_EXCL|O_WRONLY, 0600)`、`ftruncate(fd, 262144)` 和 `close`
创建了 64 个长文件名文件。它分别对创建和 truncate 调用计时，并在事后删除
自己的文件。

| 位置/运行 | open 时间合计 | truncate 时间合计 | 整个循环 |
|---|---|---|---|
| 原生 SD 卡，原始挂载 | 6.707435 s | 0.084806 s | 6.794807 s |
| 原生 SD 卡，稍后重复 | 25.181255 s | 0.309577 s | 25.493210 s |
| 内置应用缓存，实时观测 | 约 7.88 ms | 约 0.498 ms | 约 9.1 ms |

SD 卡的结果差异很大，且这些 root 探测无法复现普通应用完整的 Steam 工作负载。
所测的内置探测并非完整的内置安装基准。在这些探测中，文件创建的开销远大于
观测到的 truncate 调用。

### `dirsync` 与失败的重新挂载对照

[Linux 挂载文档](https://man7.org/linux/man-pages/man2/mount.2.html)将
`MS_DIRSYNC` 定义为同步的目录变更。结合观测到的 exFAT 缓冲等待，这使同步的
SD 卡元数据更新成为一个有力的线索。它仍只是针对剩余整体延迟的一种推断。

一次 toybox 重新挂载尝试返回 `Invalid argument`。一次直接的 mount 系统调用
实验改变了 root 视图，但 Steam 观测到的挂载表仍显示 `dirsync`。随后一次
64 文件探测耗时 2.112288 秒；由于未能确认有效的标志变更且耗时存在波动，
这**不能证明移除 `dirsync` 能改善 Steam 预分配**。Linux 文档还指出，
在重新挂载期间更改 `MS_DIRSYNC` 的尝试会被静默忽略。

原始的有效选项已在 root 视图和应用/进程视图中恢复并核对。正式补丁不包含
任何重新挂载或 root 启动行为。

### 仍可归因于 PRoot 的部分

一个采样到的 Steam 工作线程正通过快路径跳板在 `0xffff00020` 处执行
`openat`，携带的是绝对的原生宿主路径。这确认了在实际会话中部分操作绕过了
PRoot 的路径转换。其他系统调用仍经由 PRoot。

没有进行匹配的 PRoot 对直接调用的完整预分配对照。因此，404 秒中可归因于
PRoot 的比例未知。更早的 [PRoot 性能笔记](proot-performance.md)涉及不同的
硬件和工作负载，无法补上这个缺失的百分比。

公开预分配包装函数中的 7 秒并不意味着其余 397 秒与预分配无关：libc 内部/
直接系统调用绕过、显式的大小变更和文件创建工作都可能发生在这些计数器之外。

## 未成为最终修复的实验

- **目录缓存：**主动扫描会阻塞目录打开；由创建触发的失效会反复重读不断增长
  的目录。带上限的设计也可能先读完并丢弃一个大目录再重读。一个惰性变体仍有
  182 个文件耗时 4m49s，而预分配包装函数合计只占 0.879 秒。这些是中断/恢复的
  运行，并非匹配的 A/B 基准。最终的 #221 快照完全移除了该缓存。
- **仅预分配回退：**在处理了不受支持的预分配调用后，一次 FUSE 路径的尝试
  仍然很慢。随后一次启用主动缓存的恢复运行在约 36 分钟的墙钟时间内累计了
  约 8.36 秒、1,435 次成功的预分配调用。仅成功的包装函数并不足够。
- **通过 root 启动 Steam：**实验性包装函数导致合成器启动失败。它们没有产生
  预分配测量数据，已被回退。
- **更改挂载标志：**未能证明从 Steam 视图中有效移除 `dirsync`。探测中看似
  的提速并不是一个经过验证的修复。
- **替换 PRoot 或重新格式化存储：**这里没有验证任何此类替换、可移动存储
  转换或 ext4 loop 镜像部署。

早期的 FUSE 运行使用了部分暂存状态。其文件数和耗时不得与全新的 2,216 文件
运行相比并当作精确的提速倍数。

## 安装后的启动与独立的内存故障

部署 #221 + #229 + #233 之后，通过 Steam 启动了已安装的 SD 卡游戏。首次运行
的 Proton 前缀初始化先于游戏窗口出现。

在 **18:10:45**，合成器从 Steam Big Picture 切换到 **1000xRESIST**，并收到
该游戏的 1280×720 GPU 帧。一张截图显示了游戏加载画面和加载动画。主菜单或
持续的游戏过程未得到验证。

在 **18:13:48.454**，Android 记录前台应用退出，原因为 3，
`LOW_MEMORY`，主应用 PSS 227 MB、RSS 344 MB。这些数字描述的是该进程，
而不是完整的原生进程树或其峰值内存占用。随后的 gamescope/reaper 关闭消息
出现在父进程被杀之后。

这发生在安装完成之后。它是一个独立的、尚未解决的启动/内存问题，不会推翻
预分配/下载成功的结论。被杀之后的空闲内存读数无法确立峰值内存压力。

## 遗留问题与下一步有用的测试

1. 在内置存储和次级存储上使用相同的清单、保持设备唤醒且无竞争性基准，
   运行同样的全新游戏安装。分别对比预分配、下载/暂存和提交。
2. 让文件创建/扩展工作负载分别经由 PRoot 和普通应用的直接系统调用路径运行
   并匹配。保持 UID、文件系统、名称和大小一致，重复运行并记录后台 I/O。
   这可以在不改变存储语义的前提下量化剩余的 tracer 影响。
3. 在把提速归因于挂载标志之前，先建立同步目录行为上的真实受控差异。
   仅凭一个重新挂载返回码是不够的；这与可移植的应用补丁是两回事。
4. 在 enforcing SELinux 与未 root 设备下验证原生路径回退，并测试接近 ENOSPC
   以及中断之后的预分配行为。若访问或预留校验失败，保留配置路径回退。
5. 调查低内存退出，收集加载期间的进程树/cgroup 内存与 Android 杀进程证据。
   将其与安装性能分开看待。

到目前为止，一次全新的 SD 卡安装和绑定回归已得到验证。内置存储速度持平、
